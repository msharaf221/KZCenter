### 1.2 سياسات RLS في Supabase مفتوحة لأي حد معاه الـ anon key 🚨
- **الدليل:** `supabase_schema.sql:342-405` — 16 سياسة كلها بنفس الشكل:
  ```sql
  CREATE POLICY "app_all_users" ON users FOR ALL
    USING (auth.role() IN ('anon', 'authenticated'))
    WITH CHECK (auth.role() IN ('anon', 'authenticated'));
  ```
  والـ anon key نفسه متخزن في `localStorage` / مبني في الـ bundle (`src/lib/supabase.ts:9-30`).
- **الأثر (خطير جداً):**
  - `users` فيها **bcrypt password hashes** لكل المستخدمين → أي حد يقدر `SELECT * FROM users` ويسحب الهاشات ويكسرها أوفلاين.
  - `backups` فيها عمود `data_snapshot JSONB` = **نسخة كاملة من قاعدة البيانات كلها** (`dailyBackup.ts:161-168`) → readable للـ anon كمان. يعني كل الطلاب والدفعات والمديونيات متاحة للعامة.
  - `FOR ALL` مع `WITH CHECK` مفتوح = أي حد يقدر **يعدّل ويمسح** أي صف.
  - والتطبيق أصلاً **ما بيسجلش دخول في Supabase** (مفيش أي استخدام لـ `supabase.auth`)، فمفيش `auth.uid()` ولا أي عزل بين المستخدمين.
- **ملاحظة:** README بيقول «RLS Policies محسنة — سياسات أمان مفصلة لكل دور (admin/teacher) وعزل البيانات بين المستخدمين» — **ده غير مطابق للكود الموجود**.
- **الحل:**
  - شيل `users` و `backups` من المزامنة entirely (أو على الأقل امنع رفع `password_hash`).
  - فعّل **Supabase Auth** (email/password) وسياسات مبنية على `auth.uid()` + جدول `user_roles` و `user_centers` للعزل.
  - `backups` تتحط في **Supabase Storage** (bucket خاص) مش جدول JSONB، أو policy مقيّدة بـ `auth.role() = 'authenticated'` + فحص الدور.
  - لو مش هتعمل backend: خلي Supabase **مختفي تماماً** من النسخة الويب العامة، واكتفي بـ Electron/محلي.

### 1.3 مفيش مزامنة حقيقية بين الأجهزة — والسحب **مدمّر**
- **الدليل:** `src/lib/storage.ts:85-105` — `syncCloudToLocal` بيعمل `dbClearStore(table)` وبعدها `dbBulkAdd` لكل جدول. مفيش مقارنة `updated_at`، مفيش حل تعارضات، مفيش طابور أوفلاين، مفيش realtime.
- **الأثر:** مركز فيه جهازين (استقبال + إدارة) = آخر جهاز يعمل «تنزيل من السحابة» **يمسح** شغل الجهاز التاني لو السحابة أقدم. ولو التنزيل فشل في نص الجدول، بتفضل قاعدة البيانات ناقصة.
- **الحل (مهم جداً كقرار منتج):**
  - **الخيار الأسرع:** مزامنة على مستوى الصف مع مقارنة `updated_at` (last-write-wins) + سجل تعارضات يُعرض للمستخدم + طابور تغييرات أوفلاين (`outbox`) يتزامن تلقائياً.
  - **الخيار الصح:** نقل مصدر الحقيقة لـ Supabase/Postgres مع **Realtime** subscriptions، وIndexedDB يبقى كاش أوفلاين. ده الحل الوحيد اللي يخلي أكتر من مستخدم يشتغلوا في نفس اللحظة من غير ما يضيّعوا بيانات.

### 1.4 جدول **الأقساط (المديونيات)** مش بيتزامن للسحابة أصلاً

## 14) 🧭 قرار معماري لازم يتاخد دلوقتي

النظام **local-first** (IndexedDB مصدر الحقيقة) وده قرار له تمن:

| | local-first (الحالي) | Supabase كمصدر حقيقة |
|---|---|---|
| جهاز واحد / صاحب المركز بس | ✅ مثالي: سريع، يشتغل من غير نت، مجاني | ⚠️ مبالغة |
| جهازين+ (استقبال + إدارة) | ❌ مزامنة يدوية مدمّرة، تعارضات، بيانات بتضيع | ✅ realtime + عزل + audit حقيقي |
| موبايل/بوابة ولي أمر | ❌ مستحيل | ✅ ممكن |
| الأمان | ❌ كل حاجة في المتصفح | ✅ (لو RLS صحيحة) |

**توصيتي:** لو المركز هيشتغل بجهاز واحد → ركّز على P0 + P1 (الفلوس والرواتب) وسيبك من السحابة. لو فيه أكتر من جهاز أو خطة لبوابة ولي أمر/موبايل → **انقل مصدر الحقيقة لـ Supabase مع Auth و RLS صحيحة و Realtime، وخلّي IndexedDB كاش أوفلاين**، واعمل ده **قبل** ما البيانات تكبر، لأن الترحيل بيتألم كل ما البيانات تزيد.
