# هيكل النظام بعد إعادة التنظيم

**تاريخ المراجعة: 24 سبتمبر 2026**

إعادة تنظيم تدريجية للكود، وليست إعادة كتابة للبرنامج. الهدف فصل مسؤوليات التخزين وقواعد الحساب والعمليات والشاشات، مع الحفاظ على البيانات والعقود القديمة وواجهة العربية RTL.

## 1. خريطة المسؤوليات

| المكان | مسؤوليته |
|---|---|
| `src/app/routes.ts` | تعريف المسارات العشرين، التحميل الكسول، الكيان المطلوب للصلاحيات، ترتيب وأيقونات القائمة الجانبية. |
| `src/domain/models.ts` و`domain/audit.ts` | عقود الكيانات وسجل المراجعة. لا تخزين أو React. |
| `src/domain/reporting/` و`domain/backup/` | حسابات التقارير النقية وسياسة الإيراد، وتحقق ملفات/تفضيلات النسخ وسياسة موعد التشغيل. |
| `src/domain/ledger/` | توزيع التحصيل وأرصدة الطلاب والمديونيات ومرشحو التجديد وسياسات التسعير والتصفير؛ حسابات نقية بمدخلات صريحة. |
| `src/domain/payroll/` | التحقق من اتفاق المدرس والحساب والتقريب وتخطيط تسوية السلف، باستخدام بيانات ممرّرة للدوال. |
| `src/domain/settings.ts` و`studentIdentity.ts` | إعداد مسودة الإعدادات والتحقق منها، وكشف تكرار الطلاب. |
| `src/data/` | اتصال IndexedDB المشترك، المخطط المكتوب بالأنواع، القراءة والكتابة العامة وسياسة المخازن. |
| `src/services/` | عمليات التسجيل والتجديد والتحويل والأرصدة والتحصيل والاسترداد وإبراء الذمة والصيانة والنسخ الاحتياطي. |
| `src/services/backup/` و`data/backupPreferences.ts` | التنفيذ والنقل المحلي والاستعادة والمجدول وحالته المشتركة، وتخزين التفضيلات والسجل. |
| `src/services/billing/unitOfWork.ts` | وحدة عمل مالية مكتوبة بالأنواع: معاملة واحدة للتسجيل/الأقساط/الدفعات/الأرصدة/العضوية والعدادات. |
| `src/services/payroll/` | قراءة سياق الحساب، تعديل الاتفاق، اعتماد الكشوف والصرف والسلف. |
| `src/services/queries/` | تجميع بيانات قوائم الطلاب والمدرسين والمدفوعات والمصروفات والكورسات والمجموعات والمخزن والتقارير ولوحة التحكم والمرتبات. |
| `src/features/` | مكونات الإعدادات والطلاب والمدفوعات التي كانت مكدّسة داخل الصفحات. |
| `src/hooks/` و`components/ui/` | آليات التحميل، النوافذ، التأكيدات وحالات الانتظار المشتركة. |
| `src/lib/` | الأدوات المتخصصة الموجودة، مثل الفوترة والطباعة والاستيراد والصلاحيات والمزامنة؛ وواجهات التوافق القديمة. |
| `src/pages/` | توصيل حالة الصفحة والاستعلامات والخدمات بالعرض والأزرار. ليست مكاناً لتعريف مخطط القاعدة أو خوارزمية حساب الراتب. |

مسار الاعتماد الأساسي:

```text
app / pages / features / hooks
             ↓
      services / queries
             ↓
           data → domain contracts

services → domain rules → pure utilities
```

بعض المكتبات المتخصصة، مثل الفوترة والطباعة، تحتفظ بقواعدها الحالية. الاستيراد والمزامنة والمصادقة أصبح لها فصل أوضح بين الحساب/التحليل، التعامل مع التخزين أو الشبكة، وتوصيل النتائج بالواجهة. التفاصيل الإضافية أدناه.

## 2. ما لم يتغير

- اسم القاعدة **`EduCenterProDB`** وإصدارها **7**، وأسماء المخازن والفهارس ومفاتيح البيانات.
- عمل البرنامج محلياً أولاً، وSupabase اختياري. إعادة التنظيم نفسها لا تحتاج ترحيلاً جديداً أو مسح بيانات المتصفح.
- المسارات الحالية وHashRouter وبناء ملف HTML واحد، واستخدام نفس الواجهة في Electron وPWA.
- الصلاحيات في `lib/permissions.ts`، بما فيها نطاق مجموعات المدرس وربط الحساب بـ`teacherId`.
- الحذف الناعم، مفاتيح النسخ القديمة، ومفتاح `inventoryTransactions` التاريخي في التصدير.
- اتفاقات المدرسين الحالية لا تتحول تلقائياً إلى نموذج جديد.
- النسبة المطلوبة تحسب من **قيمة الاشتراك المسجل كاملة، لا المحصّل فقط**. الاعتماد يحفظ لقطة ثابتة، والصرف الجزئي أو الكامل يرتبط بمصروف راتب. التفاصيل في [دليل المرتبات](TEACHER_PAYROLL_AR.md).
- **«ربحية المجموعات» ليست في التقارير ولا تُحسب لها في الخلفية.** الدالة القديمة موجودة للتوافق مع المستدعين القدامى فقط؛ لا تستوردها صفحة التقارير.
- لا توجد مكتبات تشغيل جديدة بسبب إعادة التنظيم، ولا تغيير في سياسات RLS على خدمة حية.

## 3. التوافق مع الكود القديم

`src/lib/db.ts` و`src/lib/payroll.ts` أصبحا واجهتي **إعادة تصدير صريحتين**، لا نسختين من المنطق. أسماء الدوال والأنواع العامة القديمة محفوظة، بما فيها إعادة تصدير أنواع الفوترة.

في الكود الجديد استورد من صاحب المسؤولية:

```ts
import type { Student } from '../domain/models';
import { readAll, readSnapshot } from '../data/readers';
import { enrollStudent } from '../services/enrollmentService';
import { calcTeacherPayroll } from '../domain/payroll/calculate';
import { payPayroll } from '../services/payroll/records';
```

القراءة الجديدة تستنتج النوع من المخزن. تبقى دوال `dbGetAll` وغيرها في واجهة التوافق القديمة، ولا يستخدمها كود الإنتاج الجديد:

```ts
const students = await readAll('students'); // Student[] — خطأ القراءة يرفض الوعد
const snapshot = await readSnapshot(['payments', 'refunds', 'expenses']); // معاملة قراءة واحدة
```

اكتب اختبارات الـspies/mocks على **الوحدة المالكة**. مثلاً اختبر توليد المعرّفات عبر `lib/ids`، لا عبر واجهة `lib/db` التي لم يعد كود الإنتاج يستوردها. `publicApi.test.ts` يثبت أسماء التصدير والتوجيه إلى نفس التنفيذ، وتظل اختبارات الحسابات القديمة تستخدم الواجهات السابقة.

## 4. التخزين والعمليات

- `data/database.ts` يشارك محاولة فتح واحدة بين المستدعين المتزامنين، ويعيد ضبطها عند الفشل أو الإنهاء غير المتوقع، ويغلق الاتصال عند طلب ترقية من عميل آخر. `closeDatabase()` متاح للاختبارات ودورة حياة الاتصال.
- `data/schema.ts` يربط كل مخزن بنوع سجله. الأنواع لا تستبدل التحقق من ملفات الاستيراد أو المدخلات الخارجية وقت التشغيل.
- `data/readers.ts` هو مسار القراءة في كود الإنتاج: `readAll` و`readById` و`readByIndex` و`readPage` ترفض الوعد عند فشل التخزين. `readSnapshot` يجمع المخازن المطلوبة في معاملة قراءة واحدة. المحذوفات مستبعدة افتراضياً، ويمكن تضمينها صراحةً للتصدير والمزامنة.
- `data/records.ts` يحتفظ بسلوك القراءات القديمة فقط للتوافق: تسجيل الخطأ وإرجاع قائمة فارغة/`undefined`. هذه الأغلفة تفوّض القراءة للمصدر الجديد، ويحظر الحارس استيرادها في كود الإنتاج.
- `dbBulkAdd` يحتفظ بسلوك upsert، ويجهض المعاملة عند فشل سجل لاحق. كذلك `backupService.importAllData` يتحقق أولاً من حاويات النسخة ومعرّفات السجلات، ثم يستبدل **كل المخازن الموجودة في النسخة والإعدادات داخل معاملة واحدة**. أي فشل كتابة يرجع المعاملة كلها؛ المخازن غير المذكورة تبقى كما هي.
- `lib/pagination.ts` يجمع الترتيب والتقسيم دون تعديل المصفوفة الأصلية؛ القيم غير الصالحة للصفحة/الحجم تُطبّع إلى حدود آمنة.
- `data/stores.ts` هو مصدر قوائم النسخ والمزامنة. **`users` لا يُزامَن**. النسخ المحلية قد تضم المستخدمين وهاشات كلمات المرور للاسترجاع؛ نسخة السحابة تستبعدهم كما كانت.
- قواعد التسجيل والتحصيل والتحويل والصرف تبقى في الخدمات. عند تعديل عملية مالية مترابطة، حافظ على معاملات IndexedDB القائمة، ولا تنتظر شبكة أو تفاعل مستخدم داخل معاملة كتابة.
- صيانة بدء لوحة التحكم تحتفظ بعلامتي `migration_installments_v1` و`migration_balances_v1`. `startupMaintenance` يمنع تكرار التشغيل المتزامن، ولا يضيف ترحيلاً جديداً.
- تنظيف عضوية الطلاب المحذوفين عند فتح كتالوج المجموعات سلوك موروث محفوظ في `groupService.cleanGroupMembers`؛ لا تضف عمليات مالية كآثار جانبية إلى استعلامات العرض.

هذه الضمانات **محلية**. لا تحوّل المزامنة الاختيارية إلى معاملة موزعة بين أجهزة، ولا تحل تعارض الصرف من جهازين. إرشادات الجهاز المسؤول عن الصرف ما زالت تنطبق.

## 5. تحميل الصفحات بأمان

`useAsyncResource` يجمع حالات `data / loading / error` ويعيد `reload` ثابت الهوية:

- أحدث طلب هو الذي يحدّث النتيجة، حتى لو وصلت نتيجة بحث قديمة متأخرة.
- نتائج وأخطاء الطلبات الملغاة منطقياً لا تغيّر التحميل الحالي ولا ترسل إشعاراً قديماً.
- يحتفظ بآخر بيانات ناجحة أثناء التحديث أو فشل إعادة القراءة.
- لا يبدأ قراءة عندما يكون `enabled: false` أو بعد إلغاء تركيب المكوّن.
- callback قديم ينادي `reload` بعد حفظ منتظر سيستخدم **الفلاتر الحالية**.
- متوافق مع إعادة تشغيل effects في React StrictMode.

```tsx
const query = useCallback(
  () => loadPaymentsList({ page, pageSize: 20, search, statusFilter }),
  [page, search, statusFilter],
);
const { data, loading, error, reload } = usePageResource(query, {
  students: [], courses: [], payments: [], total: 0, refunds: [],
});
// بعد جميع الـhooks وقبل عرض النتائج أو شرط requestedId في الملفات الشخصية:
if (error) return <PageReadError title="المدفوعات" onRetry={reload} />;
```

`usePageResource` يضيف إشعار خطأ عربي موحّداً؛ `PageReadError` و`ResourceError` يعرضان حالة واضحة وزر إعادة المحاولة بدلاً من عرض أصفار أو قائمة فارغة على أنها نتيجة ناجحة. للشاشات ذات رسالة خطأ خاصة أو شرط صلاحية استخدم `useAsyncResource` مباشرةً، كما في المرتبات. لا تمرّر loader جديداً غير محفوظ بـ`useCallback` في كل render، إلا إذا كان دالة مستقرة مستوردة من وحدة.

الإلغاء هنا يمنع **نشر النتائج القديمة في React**؛ لا يلغي طلب IndexedDB فعلياً ولا يرجع كتابة أو معاملة بدأت بالفعل. المعاملات والأزرار المالية تحتفظ بحماياتها الخاصة.

## 6. الواجهات وحالة النماذج

- `SettingsPage` يجمع أقساماً مستقلة. الأقسام العامة والإيصالات والمظهر والإشعارات تتشارك **نفس المسودة ونفس مسار التحقق والحفظ**؛ لم تتحول إلى نسخ إعدادات منفصلة متعارضة. السحابة وكلمة المرور والصيانة تمتلك حالاتها المحلية.
- `useStudentEditor` يمتلك فتح/إعادة ضبط نموذج الطالب والأسعار ودفعات التسجيل وأرقام الحصص. `StudentFormDialog` يعرضه، وتبقى عمليات الحفظ على الخدمات نفسها.
- نوافذ تسجيل الدفعة والإلغاء والاسترداد منفصلة، ورصيد الطالب ومعاينة الإيصال مربوطان بمفتاح الطالب/التاريخ الصحيح لمنع عرض نتيجة الطالب السابق.
- `DialogFrame` مشترك بين `Modal` و`ConfirmDialog`: عنوان ووصف قابلان للقراءة، حجز التمرير حتى إغلاق آخر نافذة، حصر Tab، إغلاق أعلى نافذة بـEscape، واستعادة الفوكس. التأكيد يبدأ على زر الإلغاء، وليس الإجراء المدمر.
- `useConfirmDialog` يحسم الطلب المنتظر بـ`false` عند الخروج أو استبداله بتأكيد آخر، بدلاً من تعليق المستدعي. لا يستخدم نافذة النظام الأصلية، وحماية فوكس Electron موجودة كما كانت.
- أزرار الطلاب تلتف على الشاشات الضيقة بدلاً من توسيع المستند. الجداول الكبيرة تحتفظ بتمريرها الأفقي الداخلي.

## 7. حواجز تمنع الرجوع إلى التشابك

```bash
npm run check:architecture
npm run check:pii
npm run verify
```

حارس الهيكل يستخدم TypeScript الموجود بالفعل في المشروع، ويمنع:

1. استيراد واجهات التوافق المسجلة في `architecture.config.mjs` في كود الإنتاج الجديد.
2. اعتماد التخزين أو الدومين على الصفحات والخدمات الأعلى منهما، واعتماد الدومين غير المباشر على التخزين.
3. دورات الاستيراد **التنفيذية الثابتة**. الاستيرادات الممحوة بالأنواع لا تُحسب دورة؛ التحميل الكسول للمسارات ليس حافة تنفيذ متزامنة.
4. استخدام `any` داخل طبقة `data`.
5. إعادة استيراد حساب ربحية المجموعات في التقارير واستعلامها وحساباتها، حتى ديناميكياً.
6. القراءات القديمة التي تخفي الفشل في كود الإنتاج، وكتابات الواجهة الخام بما فيها إعادة التصدير والاستيراد الديناميكي.
7. أي ملف مصدر TypeScript يتجاهله Git، حتى لا ينجح البناء اعتماداً على ملف لن يصل إلى نسخة العمل التالية.

التحقق موصول بـCI، وlint لا يقبل تحذيرات في CI. حارس PII المحلي يشمل الملفات الجديدة ويحترم `.gitignore`؛ هو حارس لأنماط **أسماء ملفات البيانات**، وليس ماسحاً شاملاً لمحتوى الأسرار. لا تضع بيانات طلاب حقيقية أو نسخاً احتياطية في الريبو.

## 8. التحقق من هذا التغيير

- اختبارات الوحدات والتكامل والواجهات، بما فيها العقود السابقة وحالات المال، وصلاحيات المسارات والتحميل والنوافذ ونماذج الإدخال.
- اختبارات فتح/إغلاق/فشل/إنهاء/حجب اتصال IndexedDB، المحافظة على الترقية السابقة v6→v7، التراجع عن دفعة تالفة، والتصدير القديم واستنتاج الأنواع.
- بناء الإنتاج كملف HTML واحد؛ وفحص TypeScript وlint وحدود الطبقات.
- تحقق RLS محلي داخل PGlite: **19 فحصاً ناجحاً**، بدون تشغيل SQL على مشروع Supabase حي.
- مراجعة Chromium على بناء الإنتاج: دخول ولوحة تحكم وكل المسارات الأخرى، بما فيها الملفان التفصيليان. لا أخطاء JavaScript في هذه الجولة.
- مراجعة المرتبات بعروض **1440 و1024 و390**، والطلاب والمدفوعات والإعدادات والتقارير بعرض **390**، بدون توسيع المستند خارج الشاشة.
- تجربة وهمية مستقلة: اشتراكات 600 × نسبة 60% = مستحق 360، اعتماد واحد ثم صرف 100، ومصروف مرتبط واحد، مع بقاء تحصيل الطلاب صفراً. بيانات المتصفح التجريبية معزولة عن بيانات المستخدم.

راجع نتيجة `npm run verify` عند كل تغيير تالٍ؛ أرقام الاختبارات وحجم البناء ليست عقداً ثابتاً. هذه مراجعة للويب والبناء؛ لا تعني اختبار مُثبّت Electron على ويندوز/ماك أو مزامنة سحابية حية.


## 9. المرحلة الأعمق: الاستيراد والمزامنة والمصادقة

### الاستيراد

- `domain/imports/`: عقود السجلات، أسماء الأعمدة، تطبيع النصوص والأرقام، وتحليل صفوف شيت المركز والجداول العادية. هذه الدوال لا تفتح IndexedDB ولا تحمل ExcelJS.
- `data/files/excel.ts`: فك ملفات Excel فقط، مع قارئ خلايا واحد يدعم الخلايا المركبة والصيغ والأعمدة الفارغة ومقاطع `Uint8Array`. الفرق التاريخي محفوظ: الشيت يحتفظ بالتوقيت الكامل، والجدول يحتفظ بتاريخ اليوم.
- `services/imports/readFiles.ts`: اختيار قارئ CSV/JSON/Excel وتجميع التبويبات. `sheet.ts` و`table.ts` يطبقان الاستيراد باستخدام خدمة التسجيل الموجودة، دون تغيير أسعار أو اتفاقات موجودة تلقائياً.
- `features/imports/`: متحكم لكل نافذة و`useFilePreview` مشترك. المعاينة مرتبطة بالملف المختار؛ قراءة ملف قديم لا تستبدل الأحدث، ولا يبقى الملف السابق قابلاً للاستيراد أثناء قراءة ملف آخر. الكتابة لها حارس فوري ضد الطلب المكرر.
- `lib/sheetImport.ts` و`tableImport.ts` و`tableImportDb.ts` واجهات توافق فقط. أسماء التصدير السابقة مغطاة باختبارات، مع استمرار اختبارات المطابقة والاستيراد القديمة.

### المزامنة والنسخ السحابي

- `data/cloud/` يمتلك إعدادات الاتصال والعميل وعقود مخطط السحابة؛ مفاتيح الإعدادات المحفوظة لم تتغير.
- `domain/sync/` يمتلك تحويل المفاتيح، إزالة الحقول الحساسة، قرار الدمج وتقارير النتائج.
- `services/sync/engine.ts` لا يعتمد على Supabase أو React أو الإشعارات. يستقبل منفذي تخزين ونقل (`ports.ts`) ويمكن اختبار فشل كل دفعة أو صفحة بدون شبكة.
- `transport.ts` يقرأ صفحات مرتبة بالمعرّف، ويثبت عميل السحابة طوال التشغيل. فحص الجلسة مشترك **لكل عميل**، ولا تنتقل نتيجة جلسة مشروع إلى مشروع آخر.
- `actions.ts` يربط المحرك بـIndexedDB والإشعارات. القراءة تشمل المحذوفات: الحذف الناعم يصل للسحابة، والصف السحابي القديم لا يعيد سجلّاً محلياً حُذف بتاريخ أحدث.
- صف متكرر في صفحات السحب يقارن بآخر نسخة قُبلت، وليس بالنسخة القديمة وقت بدء القراءة. `tenant_id` و`tenantId` لا يكتبان محلياً ولا يعاد رفعهما، وحقول كلمات المرور لا تنتقل في الصفوف.
- النسخ السحابي يعيد استخدام نفس المحرك ونفس مفاتيح التعارض. كائن `settings` المفرد في نسخة التصدير يتحول إلى صف، ولا يُتخطى لأنه ليس مصفوفة. بيانات النسخة السحابية تنظّف أيضاً قبل تخزين ملفها؛ النسخ المحلية تظل تحتفظ بما تحتاجه لاستعادة المستخدمين.
- `lib/storage.ts` و`lib/supabase.ts` واجهات توافق. ثابتَا `supabase` و`isSupabaseConfigured` يحتفظان بدلالة اللقطة القديمة؛ الكود الجديد يستخدم الدوال الديناميكية من `data/cloud/client.ts`.

لم تتحول المزامنة إلى قفل موزع أو نسخة متسقة لحظياً عبر كل الجداول. قرار الدمج ما زال last-write-wins بالتواريخ الحالية، والفشل الجزئي ظاهر في التقرير. اختبارات النقل تستخدم منافذ وSDK وهميين؛ لا اتصال ببيانات مركز حقيقية.

### الإعدادات والمستخدمون

- `services/settingsService.ts` يقرأ الصف الحالي ويعدل جزءاً منه داخل معاملة واحدة، حتى لا تلغي كتابة العملة مثلاً تغيير اسم المركز المتزامن. تبديل المظهر يقرأ القيمة الحالية أيضاً، والمفتاح يظل `main`.
- `AppContext` يمتلك حالة العرض فقط؛ تطبيق CSS في `app/theme.ts`. تحميله يستخدم الحماية المشتركة من النتائج المتأخرة.
- `services/auth/` يفصل فحص كلمات المرور ومحاولات الدخول عن نشر الجلسة في React، ويفصل إدارة المستخدمين عن الواجهة.
- فحص الاسم المكرر وحذف آخر مسؤول وإعادة تعيين كلمة المرور تستخدم قراءة حديثة داخل معاملة، لا قائمة مستخدمين قديمة من الواجهة. إعادة التعيين لا تمسح ربط المدرس أو حقولاً تغيرت بالتزامن.
- `AuthContext` لا يقبل نتيجة تسجيل دخول انتهت بعد الخروج أو بعد محاولة أحدث أو بعد إلغاء تركيب المزود. انتهاء الجلسة وتغيير كلمة المرور الافتراضية والصلاحيات المحلية تبقى كما كانت. الجلسات القديمة التي تحتوي هاشاً تنظف عند استرجاعها.
- هذه ليست خدمة مصادقة خلفية جديدة: النظام ما زال محلياً، وحساب المركز السحابي مستقل عن حسابات المستخدمين المحلية.

### الملفات التفصيلية والمسودات الأكاديمية

- بيانات ملف الطالب وملف المدرس والاختبارات والمديونيات والحضور انتقلت إلى استعلامات مستقلة. نتيجة ملف شخصي مفقود لا توجه المتصفح من طلب قديم بعد الانتقال لملف آخر.
- `useResourceDraft` يربط مسودة الحضور أو الدرجات **بلقطة القراءة المحددة**. تغيير المجموعة/اليوم/الاختبار أو إعادة التحميل لا ينقل التعديلات القديمة إلى السجل الجديد، والحفظ ينتظر اكتمال القراءة الحالية.
- أيام ما قبل التحاق الطالب ونطاق مجموعات المدرس وقواعد الحساب والدفع لم تُستبدل بخوارزميات جديدة.

واجهات التوافق المسجلة (أصبحت عشراً بإضافة `lib/dataQuality.ts` و`lib/receipts.ts`) موجودة في `architecture.config.mjs`؛ ESLint وحارس الهيكل يشتركان في نفس القائمة، فلا يلزم تحديث قائمتين منفصلتين عند إضافة واجهة توافق مستقبلاً.

**نتيجة التحقق بعد المرحلة الثانية:** 901 اختبار ناجح في 52 ملفاً، و3 اختبارات متخطاة موجودة مسبقاً. `npm run verify` وفحص أنواع Electron نجحا؛ تحقق RLS المحلي نجح في 19 حالة، ومفاتيح التعارض في 23 جدولاً. مراجعة Chromium شملت الدخول والخروج وإعادة الدخول، المسارات العشرين، استيراد CSV فعلي ببيانات وهمية، حفظ الحضور والدرجات، واعتماد/صرف المرتبات، بدون أخطاء JavaScript. مراجعة العرض 1440/1024/390 حافظت على عرض المستند داخل الشاشة.


## 10. حدود أوامر الواجهة والتحقق من نسخة العمل

### مسار الكتابة

الصفحات لم تعد تستدعي `dbAdd` أو `dbPut` أو `dbSoftDelete` أو تفتح معاملات IndexedDB مباشرةً. عمليات الطلاب والمدرسين والكورسات والمجموعات والمصروفات والمخزن والاختبارات والحضور والمدفوعات تمر على `services/commands/`:

1. `access.ts`: صلاحية الكيان/الإجراء وهوية المنفذ، ونطاق مجموعة المدرس.
2. `domain/validation.ts` و`errors.ts`: تحقق مشترك من المدخلات الرقمية والتواريخ والاختيارات، وأخطاء قواعد قابلة للعرض بدون كشف تفاصيل البنية الداخلية.
3. قراءة حديثة من القاعدة، لا إعادة كتابة كائن قديم من React. مسودة الطالب لا تستبدل رصيده أو عضويته، ومسودة المجموعة لا تستبدل قائمة طلاب تغيرت أثناء التحرير.
4. `data/transactions.ts`: إنهاء/إجهاض موحد للمعاملات. لا تنتظر شبكة أو نافذة تأكيد داخل callback المعاملة.
5. أثر مراجعة بعد نجاح الحفظ. فشل تسجيل أثر إضافي لا يُقدَّم للمستخدم كأن العملية الأصلية لم تحدث، حتى لا يكررها بالخطأ.

`useCommandTask` يمنع بدء العملية مرتين قبل أول إعادة رسم، ويوحد حالة الانشغال وإظهار الخطأ. التنقل لا يلغي كتابة بدأت بالفعل. `isActive()` يسمح لمتحكم النافذة بتجاهل إغلاق/تحديث واجهة جديدة بعد انتهاء حفظ بدأ في نافذة أُغلقت. الخدمات القديمة وواجهات التوافق باقية، والعمليات المالية المعقدة تستمر في استخدام خدمات الفوترة والمرتبات المعتمدة.

### ضمانات محددة، وليست معاملة موزعة شاملة

- دفعة درجات واحدة أو كشف حضور واحد يُحفظ بالكامل أو يُجهض بالكامل. كل الدرجات تُراجع قبل الكتابة، وتُرفض قائمة حضور قديمة إذا تغير طلابها، بدل تسجيل غياب لطالب لم يظهر للمستخدم.
- التحصيل من دفعة معلقة يقرأ حالتها الحالية ويحدث الإيصال والحالة في معاملة واحدة. تكرار نفس الطلب لا يحجز إيصالاً آخر. `data/receiptCounter.ts` مشترك مع `lib/receipts.ts` ويحافظ على مفاتيح العدادات وصيغتها.
- توزيع التحصيل وتحديث الرصيد جزء من نفس المعاملة الخاصة بالعملية المالية الواحدة. منذ المرحلة السادسة يشمل ذلك حفظ ملف الطالب وتسجيلاته المتعددة ودفعاتها، وحذف المجموعة أو دفعة الطلاب المحددة بالكامل. استيراد الملف يظل يعالج صفوفه بصورة مستقلة؛ لا يوجد قفل موزع بين الأجهزة.
- تعديل/حذف مصروف راتب مرتبط ممنوع بناءً على الصف الحالي، حتى لو واجهة التحرير كانت تحمل نسخة أقدم بلا رابط. الحذف اليدوي للدفعة المسددة ممنوع؛ مسار الإلغاء المحاسبي هو البديل.
- تعديل الاسم الأكاديمي للمدرس لا يعيد كتابة اتفاق مالي أحدث إذا لم يغيّر المستخدم حقول الاتفاق. الكشوف المعتمدة وحساب النسبة من كامل الاشتراك لا تتغير.

### الصلاحيات والجلسات

كتالوج المجموعات والبحث وملف الطالب المباشر يلتزمون بنطاق المدرس، وليس فقط صفحة قائمة الطلاب. إحصاء الحضور لا يضم مجموعات مدرس آخر. بحث المدرس بلا نطاق معروف يرجع بلا نتائج، وليس كل البيانات.

الجلسة المحلية تُراجع عند الاسترجاع مقابل صف المستخدم الحالي؛ الدور القديم المحفوظ لا يطغى على الدور الحالي، والحساب المحذوف لا يسترجع جلسته. الأدوار غير المعروفة ترفض. الصفحات المحمية تحوّل الحساب الذي يحتاج تغيير كلمة المرور إلى شاشة التغيير، وتشمل الشاشة كلمة المرور الحالية حتى يعمل التغيير بعد إعادة التحميل.

إعادة تعيين القاعدة المحلية انتقلت إلى `localRecoveryService.ts`: تتطلب بيانات حساب مسؤول صحيحة وتأكيداً صريحاً، وتغلق الاتصال قبل الحذف. **هذه عملية مدمرة للبيانات المحلية فقط؛ احفظ نسخة احتياطية أولاً.** لم تُنفذ على بيانات المستخدم أثناء العمل. الصلاحيات هنا حدود تطبيق محلي، وليست بديلاً عن أمن نظام التشغيل أو عزل المستأجرين في Supabase.

### مصدر الخدمة يجب أن يُحفظ أيضاً

تم اكتشاف أن مجلد مصدر باسم `backups` كان يطابق قاعدة Git الخاصة بالنسخ الاحتياطية، مما أسقط ملف خدمة من نسخة العمل التالية. الخدمة الآن في `src/services/cloudBackupService.ts`، خارج هذا المسار، دون تخفيف حظر رفع ملفات بيانات حقيقية.

حارس الهيكل يرفض الآن:

- أي مصدر TypeScript غير متتبع يتجاهله Git داخل `src`.
- كتابة خام إلى IndexedDB من الصفحات والمكونات والـhooks والـcontexts، بما فيها aliases وnamespace imports والاتصال المباشر.

اختبارات الواجهات التي تستعمل `AuthProvider` الحقيقي تنشئ مستخدماً محلياً وهمياً عبر `test/helpers/session.ts`؛ كتابة دور في sessionStorage وحدها لم تعد طريقة صحيحة لبناء جلسة اختبار.

**نتيجة المرحلة الثالثة:** `npm run verify` ناجح: 954 اختباراً في 56 ملفاً، و3 اختبارات متخطاة مسبقاً. البناء نجح أيضاً من نسخة تحتوي الملفات المتتبعة والجديدة غير المستبعدة من Git فقط (مع إعادة استخدام الاعتماديات المثبتة)، للتحقق من عدم الاعتماد على مصدر محلي مفقود. فحص أنواع Electron و19 حالة RLS و23 هدف تعارض نجحوا محلياً. في Chromium نجحت المسارات العشرون، وتغيير كلمة مرور مطلوب بعد إعادة تحميل/رابط مباشر، وحفظ الحضور والدرجات، واعتماد 360 وصرف 100 بسند واحد، ومنع المدرس من مجموعة/ملف طالب لا يخصه ومن المرتبات. لم تظهر أخطاء JavaScript، وعرض المرتبات ظل داخل الشاشة عند 1440/1024/390. لم يُختبر مُثبّت سطح مكتب فعلي أو مشروع Supabase حي.


## 11. التقارير والقراءات والنسخ الاحتياطي

### أرقام قابلة للاختبار، لا حسابات داخل JSX

- `domain/reporting/finance.ts` يجمع تصفية الدفعات المحسوبة والاستردادات والمصروفات، تجميع الأشهر، وقياس النمو. التاريخ المرجعي وسياسة الحد الأدنى للإيراد يمران صراحةً، فلا يعتمد الاختبار على يوم تشغيله.
- `charts.ts` يحتفظ بإحصاءات الأعمار والحالة والنوع وعضويات الكورسات وامتلاء المجموعات وأداء المدرسين وفئات المصروفات؛ `daily.ts` يحتفظ بحالات وأنواع الدفعات ومقارنة الأمس واتجاه الأيام السبعة.
- **الاختلافات التاريخية مقصودة ومحفوظة:** صافي إيراد الفترة المختارة قد يكون سالباً، بينما رسوم الأشهر والتقرير اليومي ولوحة التحكم تضع الإيراد عند حد أدنى صفر. الربح قد يبقى سالباً بعد المصروفات. توزيع طرق/أنواع الدفع يعتمد إجمالي المحصّل قبل الاسترداد، والنمو مقابل فترة صفرية يظل 100% إذا كانت الفترة الحالية موجبة.
- استعلاما التقارير يقرآن البيانات المالية المرتبطة من لقطة واحدة؛ لوحة التحكم وسياق المرتبات يستخدمان قارئ اللقطة نفسه. النسخة السحابية هي لقطة محلية قبل نقلها، وليست معاملة موزعة مع Supabase.
- حسابات التقارير لا تغير أساس استحقاق المدرس؛ الاشتراكات غير المسددة تدخل في نموذج النسبة المطلوب. لا يوجد حساب أو عرض «ربحية المجموعات» في التقارير.

### الفشل ليس بيانات فارغة

- كود الإنتاج، بما فيه المزامنة والمصادقة والأرصدة، يستخدم القراءات الصارمة. عند فشل قراءة الصفوف المحلية لا يُرفع جدول فارغ بنجاح، ولا يُقبل صف سحابي على افتراض أن النسخة المحلية مفقودة.
- إعدادات الفوترة الافتراضية تستخدم عند غياب الصف/الحقول، لا عند فشل القراءة. تعذّر قراءة الاستردادات يصل إلى المستدعي بدلاً من تحويله إلى استردادات صفرية.
- حالة الخطأ في الملف الشخصي تسبق شرط تطابق المعرّف، فلا يعلق الملف في «جاري التحميل» بعد الفشل. الحضور والدرجات يحتفظان بخطأ المسودة وزر إعادة المحاولة، وطباعة كشف الحضور لا تعمل قبل اكتمال القراءة.
- تنبيه المديونيات يميّز القراءة الأولى المنتظرة، التحديث الفاشل، والنتيجة الناجحة الخالية. النسخة المخزنة مؤقتاً بعد الفشل لا تعني أن «كل الطلاب مسددين».

### النسخة المحلية: تصدير متسق واستعادة ذرية

- `exportAllData` يقرأ جميع المخازن المطلوبة في معاملة `readonly` واحدة، بما فيها المحذوفات. يبقى `includeUsers: false` مطلوباً لنسخ السحابة؛ النسخة المحلية قد تحتوي هاشات كلمات المرور اللازمة للاسترجاع ويجب حفظها في مكان آمن.
- `domain/backup/format.ts` يتحقق من جذر الملف، الإصدار المعلن، القوائم ومعرّفات الصفوف ومفتاح الإعدادات قبل أول مسح. ليس ترحيلاً شاملاً أو فرضاً لكل حقول نماذج اليوم: النسخ القديمة الجزئية والسجلات القديمة ذات المعرّف تظل مدعومة.
- الاستعادة لا تمسح المخازن المحذوفة من الملف. تقبل `inventoryTransactions` التاريخي و`inventory_transactions`، وتحتفظ بسلوك `put` وآخر صف عند تكرار معرّف. أي خطأ كتابة لاحق يُرجع جميع المخازن المشمولة والإعدادات معاً.
- يبطل كاش إعدادات الفوترة بعد الاستعادة الناجحة. أمر الواجهة يطلب صلاحية وتأكيداً صريحاً للملف **وللاستعادة الأصلية في Electron**، ثم يعيد تحميل التطبيق بعد النجاح. واجهة `lib/dailyBackup.ts` تبقى إعادة تصدير صريحة بالعقد القديم.

### تشغيل النسخ وحالة المجدول

- `services/backup/runner.ts` ينفذ الوجهات ويسجل النتيجة؛ `local.ts` للنقل المحلي؛ `restore.ts` للاستعادة؛ `scheduler.ts` للجدولة؛ `state.ts` للحالة المشتركة. لا يوجد مجلد مصدر باسم `backups` المحظور بقاعدة Git.
- قفل محلي مشترك يمنع بدء نسخ واستعادة متداخلين داخل **نسخة التطبيق نفسها**. الحالة تعرض عبر `useSyncExternalStore`؛ الخروج من الإعدادات والعودة إليها لا يفقد حالة التنفيذ أو المجدول.
- `data/backupPreferences.ts` يفصل التفضيلات القابلة للتحرير عن تاريخ آخر محاولة والعدادات والسجل. حفظ مسودة قديمة لا يرجع إحصاءات أحدث للخلف. الإعدادات والسجلات المشوهة تطبع إلى قيم آمنة، والسجل يحتفظ بآخر 100 إدخال صالح.
- نجاح حفظ الملف/النقل لا يتحول إلى ادعاء فشل كامل بسبب امتلاء تخزين السجل أو خطأ المراجعة بعد التنفيذ؛ يظهر تحذير منفصل. فشل أي وجهة عند اختيار «محلي + سحابي» يبقى فشلاً جزئياً واضحاً، ولا يزيد عداد النسخ الناجحة.
- **سياسة الجدولة لم تتغير:** تشغيل وإيقاف صريح، فحص كل دقيقة، مطابقة `HH:mm` المحلي بالضبط، ومحاولة واحدة لكل يوم محلي وفق آخر محاولة مسجلة. لا تشغيل تلقائي عند فتح التطبيق، ولا تعويض تلقائي لموعد فات أثناء إغلاقه. لا يوجد قفل بين تبويبات/أجهزة مختلفة.
- سياسة ملفات Electron الأصلية لم تتغير: ملف واحد بتاريخ اليوم، وتنظيف قديم حسب ثابت الاحتفاظ في العملية الرئيسية. تفضيل `keepDays` يُحفظ ويُتحقق منه، لكنه ليس تغييراً جديداً لسياسة الحذف الأصلية. المتصفح يطلب التنزيل ولا يستطيع ضمان قبول المستخدم للملف أو حذفه لاحقاً.

التغطية الجديدة تشمل أخطاء القراءة وإعادة المحاولة من الواجهة، رفض النسخ غير الصالحة قبل المسح، التراجع عن فشل كتابة متأخر، لقطة متسقة أثناء كتابة متداخلة، الفشل الجزئي/امتلاء التخزين، حدود اليوم المحلي، حالة المجدول بعد التنقل، ومنع مسودة إعدادات قديمة من إلغاء العدادات.

**نتيجة المرحلة الرابعة:** `npm run verify` ناجح: **1059 اختباراً في 64 ملفاً**، و3 اختبارات متخطاة مسبقاً. فحوص TypeScript وlint والهيكل وPII وبناء الإنتاج نجحت. حارس الهيكل فحص 217 وحدة إنتاج بلا دورات ثابتة. بناء مستقل من **330 ملفاً متتبعاً/جديداً ظاهراً لـGit فقط**، مع إعادة استخدام الاعتماديات، أعطى نفس ملف الإنتاج ونفس الحجم؛ لم يعتمد على أي مصدر مستبعد.

في Chromium، نجحت المسارات العشرون، وتصدير CSV وتنزيل JSON فعلي، وفشل قراءة حقيقي مع إخفاء المجاميع ثم نجاح إعادة المحاولة، واستمرار حالة المجدول بعد التنقل. نسخة تالفة لم تمسح أي جزء من البيانات، ونسخة سليمة استُعيدت مع إعادة تحميل التطبيق والمحافظة على ارتباط كشف الراتب بسند الصرف. سيناريو الاشتراكات 600 والمستحق 360 والصرف 100 بسند واحد ظل صحيحاً دون تحصيل من الطلاب. صفحات المرتبات والتقارير واليومي والإعدادات بقيت داخل عرض الشاشة عند 1440/1024/390، بلا أخطاء JavaScript. فحوص RLS المحلية الـ19 وأهداف التعارض الـ23 وفحص أنواع Electron نجحت أيضاً؛ **لم يُختبر مُثبّت Electron فعلي أو مشروع سحابي حي**.


## 12. وحدة العمل المالية وإعادة استخدام حسابات الأرصدة

### حدود المعاملة أصبحت حدود العملية فعلاً

الدوال القديمة كانت تجمع تغييرات التسجيل والأقساط والدفعات والعضوية في معاملات متفرقة. `services/billing/unitOfWork.ts` الآن يمرر مستودعاً مرتبطاً **بنفس معاملة IndexedDB** إلى كل أجزاء العملية، بدلاً من استدعاء خدمة أخرى تفتح معاملة جديدة أثناء الحفظ.

- النطاق الحالي هو `students / groups / courses / enrollments / installments / payments / refunds / counters / settings`؛ لا تغيير في قاعدة `EduCenterProDB v7` أو فهارسها.
- التسجيل وخروج الطالب والتجديد والتحويل، وتسجيل الدفعة والإلغاء والاسترداد وسداد المتبقي، وتصفير المديونيات، كلها تحدّث بياناتها المرتبطة داخل معاملة واحدة لكل استدعاء.
- حجز الإيصال وتحديث أقساطه والرصيد المحفوظ جزء من المعاملة نفسها. فشل الكتابة النهائية يرجع حتى التسجيلات والدفعات والعدادات التي سبقتها.
- التسجيل يراجع السعة والتسجيل النشط تحت قفل الكتابة. التحصيل المتزامن لا يفقد توزيع دفعة، والاسترداد يراجع صافي المدفوع الحديث، والتجديد يبني رقم دورته وتاريخها على التسجيل الحالي.
- `billingOperation` يحافظ على نتيجة `{ success, error }` لأخطاء القواعد المتوقعة؛ أخطاء I/O تُجهض المعاملة. الخدمات التي كانت تعرض نتيجة فشل صريحة تحافظ على عقدها، وحارس الواجهة يعرض خطأ مناسباً بدلاً من تسريب تفاصيل التخزين.
- المراجعة والإشعارات خارج المعاملة وبعد نجاحها، ولا تُنتظر شبكة أو نافذة أو مؤقت داخل callback المعاملة. لا يوجد قفل موزع بين أجهزة أو ضمان يعيد كل صفوف ملف استيراد مرة واحدة. حفظ ملف الطالب وتسجيلاته المتعددة أصبح معاملة واحدة في المرحلة السادسة.

### الحساب منفصل عن التخزين

- `domain/ledger/allocation.ts`: إعادة توزيع الدفعات الاشتراكية المحسوبة، بالأقدم أولاً ومع مراعاة المجموعة، دون تعديل مصفوفات المصدر.
- `balance.ts` و`types.ts`: إجمالي الطالب وتفصيل مجموعاته والمديونيات. قائمة المديونيات تستخدم لقطة قراءة واحدة وفهارس في الذاكرة، لا مجموعة قراءات جديدة لكل طالب. تواريخ الدفعات القديمة التي تحتوي وقتاً تحتفظ بدلالة «الأيام منذ آخر دفعة».
- `policy.ts` و`pricing.ts`: تطبيع سياسة الفوترة، ونقل خصومات التسجيل والسعر الخاص؛ السعر المطلق ينتقل فقط داخل نفس الكورس. معاينة التحويل والتنفيذ يستخدمان القاعدة نفسها.
- `renewals.ts`: تجميع مرشحي التجديد بمرجع زمني صريح؛ مفاتيح الطالب/المجموعة لا تتصادم إذا احتوت المعرّفات على فاصل نصي.
- قواعد الاسترداد التاريخية لم تتغير: الاستردادات تقلل صافي المدفوع، لكنها لا تعيد توزيع تغطية الأقساط تلقائياً. كذلك يظل fallback السعر الكتالوجي لتحديث إجماليات البيانات القديمة بلا أقساط مختلفاً عن رصيد العرض القائم على الأقساط. هذه فروق موثقة ومغطاة باختبارات، وليست تغييراً ضمنياً في اتفاق مالي.
- لا كتابة إلى كشوف المرتبات المعتمدة من وحدة عمل الطالب. مستحقات نموذج النسبة المطلوب ما زالت من **الاشتراك الكامل، المدفوع أو غير المدفوع**، و«ربحية المجموعات» لم تعد للواجهة أو الحساب الخلفي.

### أوامر الواجهة ومراجعة العمليات المدمرة

- `services/commands/studentFinance.ts` هو مدخل الواجهة للتحصيل والإلغاء والاسترداد والتسجيل والخروج والتجديد والتحويل والتصفير. يفحص الصلاحيات ويسجل المنفذ الحقيقي وأثر المراجعة؛ صلاحية التسجيل الأكاديمي وحدها لا تمنح حق تحصيل دفعة أولى.
- حارس الهيكل يمنع الالتفاف من الواجهة إلى دوال الكتابة المالية القديمة أو إلى وحدة العمل مباشرةً، مع السماح بالاستعلامات للقراءة. الصادرات القديمة في `lib/db` باقية لمستدعي الخدمات والاختبارات.
- نوافذ التجديد والتحويل مرتبطة بهوية الطالب/المجموعة وتبدأ بمسودة جديدة عند إعادة الفتح. لا تسمح قراءة فاشلة بحفظ تجديد، ولا تُعرض كرصيد تحويل صفر. إتمام حفظ قديم لا يغلق نافذة طالب آخر، وتغيير معرّف ملف الطالب يعيد إنشاء حالته ونوافذه.
- التصفير يقرأ ملخصاً وبصمة للأقساط من لقطة واحدة. بعد التأكيد يعاد فحص البصمة داخل معاملة الكتابة؛ إذا تغيّر النطاق الفعلي أو المبلغ، لا تُلغى أقساط لم يراجعها المستخدم، وتعرض الواجهة الملخص الجديد وتطلب كتابة التأكيد من جديد. الـAPI القديم يظل يقبل تنفيذ النطاق مباشرةً إن لم تمرّر بصمة؛ مسار الواجهة يشترطها.
- تنظيف عضوية المجموعات الموروث يراجع الصفوف الحديثة بدلاً من كتابة قائمة قديمة فوق تسجيل أحدث، ويعاد تطبيق نطاق المدرس بعد التحديث. شريط إجراءات المجموعات يلتف على الهاتف ولا يوسع المستند خارج الشاشة.

الاختبارات الجديدة تحقن فشل كتابة متأخر في تسع عمليات كاملة، وتراجع التراجع عن كل المخازن والعدادات؛ وتشغّل تسجيلات وتحصيلات واستردادات وتجديدات متزامنة؛ وتراجع الصلاحيات والبصمة القديمة وسباق تحميل النطاقات ومسودات النوافذ. تاريخ إدخال فارغ أو غير صحيح لا يُستبدل تلقائياً بتاريخ اليوم عند التنفيذ.

**نتيجة المرحلة الخامسة:** `npm run verify` ناجح: **1114 اختباراً في 68 ملفاً**، و3 اختبارات متخطاة مسبقاً. فحوص الأنواع وlint والهيكل وPII وبناء الإنتاج نجحت، مع 229 وحدة إنتاج بلا دورات ثابتة. نسخة بناء مستقلة من **346 ملفاً ظاهراً لـGit فقط** (مع إعادة استخدام الاعتماديات) أنتجت نفس HTML، دون الاعتماد على مصدر مستبعد.

مراجعة Chromium نجحت للمسارات العشرين، وتحصيل من ملف الطالب، وفشل/إعادة محاولة معاينة التجديد ثم التجديد بدفعة، والتحويل بترحيل التحصيل، والاسترداد والإلغاء، وإضافة/إزالة طالب من المجموعة، ورفض تصفير بمعاينة قديمة ثم التنفيذ بعد تأكيد جديد. كشف المرتب المعتمد من اشتراكات غير مسددة (أساس 600، مستحق 360، صرف 100 ومصروف مرتبط واحد) لم يتغير بسبب تعديلات سجل الطالب اللاحقة. قياسات عرض المستند لصفحات المجموعات والمدفوعات والمديونيات والمرتبات وملف الطالب نجحت عند 1440/1024/390؛ لا أخطاء JavaScript. فحوص RLS المحلية الـ19 وأهداف التعارض الـ23 وفحص أنواع Electron نجحت أيضاً. هذا ليس اختباراً لمُثبّت Electron أو لسحابة حية.


## 13. العمليات المركبة وصيانة البيانات

### حفظ وحذف كامل، وليس نجاحاً جزئياً مخفياً

- `services/membership/enrollment.ts` يحتوي العمل القابل للتركيب داخل وحدة عمل قائمة: التسجيل أو فصل الطالب من المجموعة. المستدعي هو الذي يملك المعاملة؛ الأخطاء المتوقعة تُرمى كي تُجهض العملية الأكبر أيضاً. `enrollmentService` يحافظ على نتيجة الـAPI القديم.
- `saveStudent` يحفظ الملف وكل الإضافات/الإزالات والدفعات الأولى والأقساط والعدادات داخل معاملة واحدة. إذا تعذّر التسجيل في المجموعة الثانية، لا يبقى ملف جديد أو دفعة/تسجيل من المجموعة الأولى. نتيجة النجاح ترجع صف الطالب الحديث، و`warnings` باقية للتوافق لكنها لم تعد وسيلة لإخفاء حفظ جزئي.
- نموذج تعديل الطالب يرسل عضويات وقت فتحه. تعديل الاسم أو المدرسة فقط يحافظ على عضوية أضيفت لاحقاً؛ أما تغيير الاختيارات نفسها فيحتاج أن تظل العضويات مطابقة للنسخة التي راجعها المستخدم. بيانات ولي الأمر والمدرسة والصف ومصدر التعارف تُحفظ عند إعادة فتح النموذج.
- حذف الطلاب المحددين معاملة واحدة للدفعة كلها. حذف المجموعة يجمع روابطها من التسجيلات والأقساط وقوائم الطرفين، ولا يعتمد على `studentIds` وحدها. السجلات النشطة المتكررة لنفس الزوج تُغلق كلها، والروابط القديمة بلا تسجيل نشط تنظّف أيضاً.
- سياسة الخروج محفوظة: الأقساط غير المسددة تُلغى، والأقساط المسددة والدفعات والاستردادات والإيصالات وسجلات المرتبات ومصروفاتها لا تُحذف. tombstone يُكتب بعد نجاح بقية العمل داخل نفس المعاملة. فشل السجل الأخير يرجع كل ما سبقه.
- حتى `dbSoftDelete` القديم يقرأ الصف ويكتب tombstone في معاملة واحدة، فلا يستبدل تعديلاً أحدث بنسخة قرأها قبل بدء معاملة أخرى.
- اختيار صفوف الطلاب أصبح ذا تسمية وحالة قابلة للقراءة بلوحة المفاتيح، و«اختيار المعروض» لا يلغي اختيارات صفحة/فلتر آخر. رسالة الحذف تحسب الأرصدة لكل المعرّفات المحددة، لا للصفحة المرئية فقط.

### التخطيط النقي ثم التطبيق داخل المعاملة

- `domain/maintenance/integrity.ts` يبني خطة روابط دون تعديل المدخلات. سجل التسجيلات هو المرجع؛ `dropped / transferred / completed` أو tombstone لا تتحول إلى تسجيل نشط بسبب قائمة عضوية قديمة. علاقات البيانات القديمة التي ليس لها أي سجل تُستكمل من أي من الطرفين، مرة واحدة.
- `services/maintenance/integrity.ts` يطبق خطة الطلاب والمجموعات والتسجيلات والإجماليات في معاملة تشمل بيانات التخطيط نفسها. لا تعود روابط شالتها خطوة سابقة، ولا تُكتب نسخة قديمة فوق تعديل متزامن. إصلاح الروابط **ليس إبراء ذمة**: لا يلغي الأقساط أو يغير مبالغها.
- حالات الأقساط المخزنة تُحدّث من قراءة تحت نفس قفل الكتابة؛ لا تضيع دفعة جاءت بالتزامن مع تعليم المتأخرات. توليد الأقساط القديمة يتسلسل مع العمليات المالية، فيمنع تكرار الخطة من استدعاءين متزامنين، ولا يولّد ديناً اعتماداً على عضوية تاريخية ملغاة/محذوفة أو على طالب مفقود. سياسة الترحيل القديمة للشهر الكتالوجي الواحد محفوظة؛ لا يُعاد تسعير قسط قائم.
- `quality.ts` و`qualityRepair.ts` يفصلان تحليل الجودة والتخطيط عن القراءة/الكتابة. الفحص يقرأ لقطة واحدة، والإصلاح يرجع تقرير ما بعد التعديل من خطته داخل المعاملة، دون قراءة لاحقة قد تفشل وتوهم المستخدم بأن الإصلاح لم يحدث.
- `services/commands/maintenance.ts` يفحص صلاحية الإعدادات ويشترط تأكيداً للربط وإصلاح المواد/الأسعار. متحكم الواجهة يمنع تداخل الأزرار، ولا ينفذ تأكيداً أُغلق أثناء الانتظار. لا تتغير الأقساط أو الدفعات أو اتفاق المدرس عند إصلاح أسعار الكتالوج الصفرية.

### إيصالات سليمة حتى وقت الصيانة

- `lib/receipts.ts` و`lib/dataQuality.ts` واجهتا إعادة تصدير فقط؛ العقود القديمة مثبتة في `legacy-public-api.json`، ويمنع الحارس الرجوع إليهما من كود الإنتاج.
- `services/receiptService.ts` يملك التخزين، و`domain/maintenance/receiptNumbers.ts` يتحقق ويخطط الترقيم. الترقيم الرجعي والعدادات يُحفظان معاً ويشتركان في نطاق قفل التحصيل؛ التشغيل المتزامن لا يخصص نفس الرقم مرتين.
- ترتيب التاريخ/وقت الإنشاء، السنوات والبادئات، ترقيم الدفعات الملغاة، واحترام أعلى رقم محجوز أو موجود حتى في سجل محذوف محفوظة. التواريخ القديمة ذات الوقت مدعومة أيضاً.
- العدّاد غير الرقمي أو السالب أو الكسري أو المستنفد لا ينتج إيصال `NaN` أو رقماً غير آمن: يتوقف الحفظ وتُرجع المعاملة. تصحيح العداد اليدوي يحتفظ بالتقريب/تصفير السالب القديم للقيم المحدودة؛ إعادة العداد يدوياً تظل إجراءً مقصوداً قد يسمح بإعادة استعمال الأرقام، وليست ضمان ترقيم موزع.
- استيراد اكتمل ثم فشل فحصه أو ربطه التكميلي يبقي تقرير الاستيراد ويعرض تحذيراً منفصلاً، بدلاً من طلب إعادة استيراد بيانات حُفظت بالفعل. عرض الإصلاح العام داخل نافذة الاستيراد مقصور على صلاحية صيانة الإعدادات.

كل ذلك محلي، بلا تغيير في مخطط v7 أو مكتبات التشغيل أو الصلاحيات السحابية. نسبة المدرس المستقلة من **الاشتراك الكامل حتى لو لم يُحصّل** والكشوف المعتمدة تبقى كما هي، ولا يوجد عرض أو حساب خلفي لربحية المجموعات في التقارير.
